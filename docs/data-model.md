# Data model and domain logic

Moved out of CLAUDE.md. Read the relevant part before touching the schema, assignments, completions, reviews or recurring sign-offs.

### Data Layer
- **Azure Blob Storage** — file storage, organized in hierarchical paths with versioning via naming convention; SAS tokens for secure temporary access (`src/lib/storage.ts`, `src/lib/file-system/`)
- **Azure Table Storage** — one table: `activityLogs` (audit trail only); accessed via `@azure/data-tables` (`src/lib/activity-logger.ts`)
- **Neon PostgreSQL + Prisma** — all relational data
  - Schema: `prisma/schema.prisma`; client generated to `src/generated/prisma/`; singleton at `src/lib/prisma.ts`; driver: `@prisma/adapter-pg`
  - Models: `Tenant`, `User`, `PasswordReset`, `CustomerCompany`, `DocumentTemplate`, `TemplateVersionHistory`, `Assignment`, `CompletionRecord`
  - `User`: nullable `email?` and `passwordHash?` (no-email workers cannot log in); nullable `jobRole?`; nullable `lineManagerId?` self-ref FK → `User.id` (routes notifications to line manager); nullable `employeeNumber?`/`dateOfBirth?` (P8 — optional kiosk sign-off identity confirmation for no-email workers, set by an admin on the user; kiosk requires whichever is set, employee number preferred when both are)
  - `DocumentTemplate`: `formSchema Json?` — array of `FormField` (`src/types/form-schema.ts`): `type` is one of `text | textarea | number | checkbox | date | select | file | section`; `select` fields carry `options: string[]`; `file` fields store an `{ blobPath, fileName }` object once uploaded; `section` fields are heading-only (no value, never required, excluded from stored `formData`); `questions Json?` — each question is `{ id, question, options: string[], answer: string }`; `version Int @default(1)` — incremented on each publish; nullable `ownerCompanyId?` — null = tenant-managed (Simon's library); set = created by that `CustomerCompany`'s admin via the self-serve portal (P17), visible only within that company; `category String @default("General")` (`DocumentTemplateCategory`, `src/types/document-template.ts` — `'COSHH' | 'Fire Safety' | 'First Aid' | 'General' | 'Manual Handling' | 'Other' | 'PPE' | 'Risk Assessment'`, also exported as `DOCUMENT_TEMPLATE_CATEGORIES`) — fixed classification used to group `/admin/templates`, editable at any time (create/edit/publish-version, snapshotted into `TemplateVersionHistory` like `title`/`description`); `sourceType String @default("form")` (`'form' | 'upload'`, `src/types/document-template.ts`) — P19 upload-based documents; `uploadMode String?` (`'read-only' | 'fill-and-return'`, upload templates only); `sourceDocBlobPath`/`sourceDocOriginalBlobPath`/`sourceDocFileName` — converted PDF (served/viewed) + retained Word original (for renewal edits) + display filename, all nullable, upload templates only
  - `DocumentTemplate` review dates (2.2): `reviewDueAt DateTime?` (defaults to `reviewPeriodMonths` after create/publish/"Reviewed — no changes"), `reviewPeriodMonths Int @default(12)` (per-template months between reviews, 1-120, validated by `isValidReviewPeriod`; new templates take `Tenant.reviewPeriodMonths` (default 12, edited on Settings → Reviews via `GET`/`PATCH /api/admin/settings/review-period`, read by `getReviewPeriodMonths`/`getReviewPeriodMonthsForCompany`) unless the create request passes its own; a company can override the tenant default for its own templates via `CustomerCompany.reviewPeriodMonths` (nullable, `GET`/`PATCH /api/customer/admin/settings/review-period`, "Review period" button on `/customer/admin/templates`; resolution order: company override, tenant default, single tenant row, 12) — the create dialogs offer a `ReviewPeriodSelect` (presets plus a Custom… 1-120 month input), and existing templates are unaffected by a default change; drives `reviewDueAt` on create/publish/"Reviewed — no changes"), `reviewOwnerId String?` (userId, defaults to the creating admin; receives reminder emails), `lastReviewedAt DateTime?`. `TemplateReview` (`templateId`, `version`, `reviewedAt`, `reviewedBy`, `note`) is the audit trail for "Reviewed — no changes", which restarts the clock *without* bumping `version` or re-assigning. Pure helpers in `src/lib/review-dates.ts` (client-safe: `computeReviewDueAt`, `getReviewStatus` → `ok | due-soon | overdue`, `isReviewReminderDay` — days 30/7/0); DB lib in `src/lib/template-reviews.ts` (`markTemplateReviewed`, `getTemplateReviews`, `getTemplatesDueForReview`, `getTemplatesNeedingReviewReminders` — tenant library only, `ownerCompanyId IS NULL`). `POST /api/admin/templates/[id]/review` records a review; the daily `GET /api/cron/reminders` emails owners via `sendTemplateReviewReminder` (response gains `reviewReminders`); `getDashboardKPIs` gains `templatesDueForReview` (overdue or due within 30 days, shown as a dashboard tile); `/admin/templates` has a "Review due" column and a "Reviewed — no changes" button; `version-history` returns `reviews` (rendered in the version-history dialog); `lastReviewReminderAt` makes reminders stateful — the latest of the 30/7/0-day milestones reached is sent once (a missed cron run catches up), then weekly once overdue, and any date reset clears it; owner-less tenant templates remind every admin, owner-less company templates nobody; `/admin/templates` has a Review settings dialog (owner + date via `PATCH /api/admin/templates/[id]`); company templates get the same column, "Reviewed — no changes" (`POST /api/customer/admin/templates/[id]/review`) and Review settings dialog (`PATCH /api/customer/admin/templates/[id]` validates period 1-120, date, and that `reviewOwnerId` is a Customer Admin of the same company; the dialog is reused with `usersEndpoint`/`ownerRoles` props; creator is the default owner); the review date also shows in the admin view dialog on the customer complete page and on both kiosk sign-off pages (`GET /api/signoff/[companyId]` returns `template.reviewDueAt`); `generateCompletionPDF` takes `templateReviewDueAt` and prints "Document review date".
  - `TemplateVersionHistory`: `templateId` FK, `version Int`, `changeReason String?`, `snapshot Json` (`{title, description, formSchema, questions, sourceType?, uploadMode?, sourceDocBlobPath?, sourceDocOriginalBlobPath?, sourceDocFileName?}` — the P19 fields are optional since pre-P19 history entries predate them), `publishedAt`, `publishedBy String?` (userId) — only ever holds *superseded* versions; the live version's content lives on `DocumentTemplate` itself
  - `Assignment`: nullable `userId` (individual vs company-wide); nullable `dueDate?`; nullable `targetJobRoles Json?` (string array); `templateVersion Int @default(1)` — snapshot at assignment creation; partial unique indexes include `templateVersion`; nullable `lastReminderSentAt DateTime?` — set by the reminders cron each time a reminder is sent for that assignment; `autoEnroll Boolean @default(false)` — company-wide only (forced `false` when `userId` is set); marks an assignment for auto-enrolment (see `enrollMatchingUsersForAssignment`/`enrollUserInMatchingAssignments` below); nullable `recurrenceMonths Int?` (2.1 recurring sign-offs — completions expire this many months after signing; carried forward by new versions and auto-enrolment); `cycle Int @default(1)` — renewal cycle within a template version, part of both partial unique indexes (`templateId, customerCompanyId|userId, templateVersion, cycle`)
  - `CompletionRecord`: `submittedBlobPath`/`submittedOriginalBlobPath`/`submittedFileName` (all `String?`, P19) hold the employee's own filled-in copy for `fill-and-return` upload templates — converted PDF + retained original, mirroring `DocumentTemplate`'s source doc fields; null for form-based templates and read-only upload templates; ``validUntil DateTime?` (`signedAt + assignment.recurrenceMonths`, set inside `createCompletionRecord`; null = never expires); `signerIp`/`signerUserAgent` (both `String?`, P8) — captured from the request on both the authenticated customer complete route and the public kiosk route, non-fatal if headers are absent
  - Lib: `src/lib/customer-companies.ts`, `src/lib/document-templates.ts`, `src/lib/template-version-history.ts`, `src/lib/template-version-diff.ts`, `src/lib/assignments.ts`, `src/lib/completion-records.ts`, `src/lib/outstanding-completions.ts`, `src/lib/form-schema-utils.ts` (`isFieldVisible` — shared by client rendering and server validation), `src/lib/form-validation.ts` (`getMissingRequiredFields`/`getVisibleFormData` — server-side required-field and visibility validation per field type), `src/lib/starter-templates.ts` (hardcoded, client-side-only form field presets for common H&S document types), `src/lib/document-conversion.ts` (`convertToPdf` — Word→PDF via the Gotenberg sidecar, P19), `src/lib/document-upload.ts` (`uploadSourceDocument` — PDF stored as-is, Word converted + original retained; used by both `POST /api/admin/templates/upload-document` and the customer-admin equivalent)
  - `Tenant.completionRetentionYears Int @default(5)` — years a signed `CompletionRecord` must be retained before an admin may delete it (UK H&S guidance: 3–5 years). Pure date logic in `src/lib/data-retention.ts` (`isWithinRetentionPeriod`/`getRetentionEndDate` — no prisma import, safe to import client-side); tenant-scoped read/write in `src/lib/user-database.ts` (`getAdminTenantId` — resolves an admin's tenant, falling back to the single tenant row; `getCompletionRetentionYears`/`updateCompletionRetentionYears`), exposed via `GET`/`PATCH /api/admin/settings/data-retention` and edited on the Settings page's "Data Retention" tab. `DELETE /api/admin/completions/[id]` enforces the guard server-side (403 while a completion is within the window); `/admin/completions/[companyId]/[templateId]` disables the delete checkbox/button and shows a lock icon with the unlock date for protected rows client-side, mirroring the guard rather than relying on the 403 alone.
  - `AssignmentWithTemplate.template` (`getAssignmentWithTemplate` et al., `src/lib/assignments.ts`) carries `sourceType`/`uploadMode`/`sourceDocBlobPath`/`sourceDocFileName` through from `DocumentTemplate` (P19) — this is how employee-facing routes know a given assignment is an upload-based document; `GET /api/customer/assignments/[id]/document` generates a SAS view URL for `sourceDocBlobPath`, 404s when the template isn't `sourceType: 'upload'`; `POST /api/customer/assignments/[id]/upload-submission` (P19 Phase 5, fill-and-return only) uploads the employee's own filled-in copy via `uploadSourceDocument()` and returns blob paths — `POST /api/customer/assignments/[id]/complete` then requires that `submission` in its body (400s otherwise) and passes it straight to `createCompletionRecord()`'s `submittedBlobPath`/`submittedOriginalBlobPath`/`submittedFileName` params
  - Key functions: `getAssignmentStatusSummary` (completed records + outstanding users + isOverdue); `getAssignmentsForUser` (filters by `targetJobRoles`, deduplicates by highest-version per templateId — individual beats company-wide at same version); `publishNewTemplateVersion` (requires `changeReason`; in one `$transaction`, snapshots the current content into `TemplateVersionHistory` then increments `version` and applies content updates); `createAssignmentsForNewVersion` (replicates all previous-version assignments at new version, carrying `autoEnroll` forward); `getOutstandingCompletions` (cross-company, one row per assignment with `outstandingCount > 0`, sorted by due date ascending); `diffTemplateSnapshots` (pure — structural diff of two `TemplateSnapshot`s by field/question `id`: added/removed/changed/unchanged); `enrollMatchingUsersForAssignment`/`enrollUserInMatchingAssignments` (auto-enrolment: creates an individual `Assignment` — an audit-trail "enrolled on [date]" record — for each company user whose `jobRole` matches an `autoEnroll` company-wide assignment's `targetJobRoles`; stricter than view-layer filtering — a user with no `jobRole` does not match a role-restricted `autoEnroll` assignment; triggered on assignment creation, user registration, and admin/self-service `jobRole` changes); `getAllDocumentTemplates` (tenant library only — `WHERE ownerCompanyId IS NULL`)/`getDocumentTemplatesByOwnerCompany` (a single company's self-serve templates — used by both the company admin's own template list and Simon's read-only view on the company detail page)
  - Prisma nullable JSON fields: use `Prisma.NullableJsonNullValueInput` / `Prisma.InputJsonValue` (imported from `@/generated/prisma/client`); the shared `toJsonValue` helper in `src/lib/prisma-json.ts` maps `undefined`/`null`/value to the correct write shape (used by `assignments.ts` and `document-templates.ts`)
- **Recurring sign-offs (2.1)**: a renewal is a new individual `Assignment` at `cycle + 1` (same `templateVersion`), not a re-opened completion. `src/lib/completion-validity.ts` (pure, client-safe — `computeValidUntil` with month-end clamping, `getValidityStatus` → `valid | expiring-soon | expired`, `DEFAULT_RENEWAL_LEAD_DAYS = 30`, `isValidRecurrenceMonths`/`isValidRenewalLeadDays`) and `src/lib/renewals.ts` (`renewExpiringCompletions` — for each completion expiring within 30 days, creates the signer's cycle N+1 assignment due on the expiry date, using the company tenant's lead time; skipped when the user re-signed, or a newer cycle/version already supersedes; idempotent). `GET /api/cron/reminders` runs renewals first (announcing each with `sendAssignmentNotification`; response gains `renewed`), then the normal reminders, which then chase the renewal's due date. `getAssignmentsForUser` picks highest version, then highest cycle, then individual-over-company-wide. The lead time is `Tenant.renewalLeadDays Int @default(30)` (1–180), read via `getRenewalLeadDays`/`getRenewalLeadDaysForCompany` and edited through `GET`/`PATCH /api/admin/settings/renewal-lead` on the Settings page's "Renewals" tab; the "Expiring soon" status is computed server-side (`validityStatus` on completion records) so clients never need the lead time. Completion views treat a lapsed completion as outstanding (`summariseUserValidity` in `completion-records.ts`; `getCompletionGroupsByCompany` adds `expiringSoonCount`/`expiredCount`, and outstanding is per distinct valid user rather than a completion count); `validUntil` is exposed on completion records, printed as "Valid until" on the signed PDF, and shown on the customer documents page, both completion-detail pages and via `RecurrenceSelect` (`src/components/recurrence-select.tsx`) on both assign dialogs. Assign routes validate `recurrenceMonths` (400 unless a whole number 1–120).
